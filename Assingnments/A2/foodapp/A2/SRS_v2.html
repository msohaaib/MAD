Assignment A2 · Restaurant App MVP

Software Requirements Specification

Bistro Nova · Version 2.0 · Revised from A1

This document updates the A1 SRS. The mobile screens, context, reducers, and hooks stay. A Node.js / Express server and a MongoDB database are now in scope so every phone reads and writes the same data.

1. Introduction

1.1 Purpose

This SRS describes Bistro Nova, a restaurant mobile application for customers and a floor manager. Version 2 adds a shared backend so menu prices, availability, orders, and reservations are no longer trapped on a single device.

1.2 Scope

In scope. Role-based login, menu browsing, cart and order placement, order tracking, table reservations, and a manager dashboard for menu, orders, and bookings. The Express API and the MongoDB database named restaurant_app are now in scope. The phone talks to the laptop (or a hosted server) over HTTP. The server is the only place that stores users, menu items, tables, reservations, and orders.

Out of scope. Real card payments, push notifications, kitchen printer integration, multi-restaurant support, and delivery tracking remain out of scope.

Problems found while using the A1 app (mock data only), and how v2 solves them.

  • A manager price change stays on one phone. A1 wrote menu edits to AsyncStorage. Another device still showed the old price. v2 stores prices in MongoDB. PUT /api/menu/:id updates the shared document. The customer list reloads with GET /api/menu.
  • Sold-out dishes stay available on other phones. The manager could flip availability locally only. v2 writes available on the MenuItems collection so every customer sees the same flag.
  • An order placed on one phone is missing on another. A1 kept orders in memory or device storage. v2 saves the order on the server. GET /api/orders/my returns the same list for that user on any device after login.
  • Reinstalling the app wipes bookings and order history. Mock files and AsyncStorage die with the install. v2 keeps Reservations and Orders in MongoDB.
  • Two guests can book the same table at the same time. Each phone checked only its own list. The server now rejects a clash with HTTP 409 before insert.
  • The cart total can be forged. A1 trusted whatever number the reducer produced. The server ignores a client total and prices every line from MenuItems.
  • Order status only moved on the phone that started a fake timer. v2 polls GET /api/orders/my every ten seconds. When the manager patches status, the customer screen updates without a restart.
  • Passwords lived in a mock users file. v2 hashes passwords with bcrypt and issues a JWT. Menu writes require a manager token.

2. Overall description

2.1 Product perspective

Bistro Nova is a single-restaurant system. The Expo app is a client. The Express process on the laptop (or a later host) is the server. MongoDB is the system of record. Phones do not share files with each other. They share the database through the API.

2.2 Product functions

  • Register and log in. The server returns a token and a user object without a password.
  • Browse, search, and filter the menu. The list comes from the server.
  • Place an order. The server computes the total and rejects unavailable dishes.
  • Track an order by polling every ten seconds.
  • Request a table. The server checks seats and time clashes.
  • Manager: create, edit, and delete dishes; toggle availability; move order status forward; accept or decline bookings.

2.3 User classes

UserAccess
CustomerPublic menu, own orders, own reservations, signup and login.
ManagerEverything a customer can do on the API that is role-open, plus menu writes, all orders, all reservations, and status changes.
Guest (not logged in)Health check and menu read only.

2.4 Constraints

  • The phone must use the laptop LAN IP, not localhost, when the app runs in Expo Go.
  • JWT expires after 24 hours.
  • Order status may only move forward, except Cancelled from Pending.
  • No payment gateway is called.

2.5 Assumptions

The restaurant has one site. Table bookings are keyed by date and time string (not overlapping duration windows). Both devices sit on the same Wi-Fi during the two-device test.

3. Functional requirements

IDRequirement
FR-01The system shall register a customer with a hashed password and reject a duplicate email with 409.
FR-02The system shall log a user in and return a JWT plus name, email, and role. The password shall never appear in a response.
FR-03The system shall restore a session from AsyncStorage on the phone after the app is closed.
FR-04Anyone may read the menu. Search on name is case-insensitive. Category may be filtered.
FR-05Only a manager with a valid token may create, update, or delete a menu item.
FR-06The server shall reject a negative price and an invalid MongoDB id with 400, and a missing item with 404.
FR-07When an order is placed, the server shall load each dish from the database, refuse unavailable items, and compute the total itself.
FR-08A customer shall see only their orders. A manager shall see all orders.
FR-09Order status shall follow Pending → Preparing → Ready → Served. Cancelled is allowed only from Pending.
FR-10The tracking screen shall poll the customer's orders every 10 seconds and clear the interval on unmount.
FR-11A reservation shall be refused if the table is missing, the party is larger than the seat count, or the table is already booked at that date and time (409).
FR-12A manager shall accept or decline a reservation. The customer list shall show the new status after refresh or return to the screen.
FR-13Unknown routes shall return 404 with the message "Route not found". Uncaught errors shall return JSON with status 500.

4. Non-functional requirements

  • Security. Passwords hashed with bcrypt. Protected routes read Authorization: Bearer <token>.
  • Availability. The API listens on 0.0.0.0 so a phone on the LAN can reach it.
  • Usability. The app keeps A1 loading, error, retry, and pull-to-refresh behaviour. Client validation still runs for quick feedback; the server decision wins.
  • Maintainability. Routes only map URLs. Controllers own database work. BASE_URL lives in one file.

6. User interface

A1 screens remain. Auth stack: Login, Signup. Customer tabs: Menu, Cart, Orders, Book, Profile. Extra stacks: dish detail, order tracking, book a table. Manager tabs: Floor, Menu, Orders, Bookings, Profile, plus the add/edit dish form. The visual language is warm paper and wine red. Screens now load through src/api/client.js and src/hooks/useApi.js instead of mock files.

7. Use cases

UC-01 Customer places an order. The customer adds dishes, opens the cart, and taps Place order. The app sends item ids and quantities. The server loads prices, rejects sold-out dishes, stores the order, and returns 201. The tracking screen starts polling.

UC-02 Manager marks a dish unavailable. The manager toggles the switch. The app calls the protected PUT. Any customer who pulls to refresh sees Unavailable and cannot add the dish.

UC-03 Customer books a table. The customer picks a table, date, time, and party size. Client validation runs first. The server checks seats and clashes, then inserts Pending.

UC-04 Manager accepts a booking and advances an order. Accept uses PATCH on the reservation. Ready uses PATCH on the order. The second phone sees both without a reinstall.

Query parameters on GET /api/menu: category (exact) and search (case-insensitive name match).
